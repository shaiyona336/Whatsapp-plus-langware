================================================================================
MOST LIKELY — what a 1-hour interview will actually ask you to do
================================================================================

How a 1-hour session usually splits:
  ~10 min  you walk them through your code / architecture
  ~25-35 min  they ask you to ADD ONE feature (or FIND/FIX a bug) live
  ~10-15 min  design discussion / "how would you..." Q&A (no code)

So the realistic asks are things doable in ~25 min IN THIS codebase, or a
bug hunt, or a whiteboard discussion. Ranked below by likelihood.

Files you'll touch most:
  backend/main.py        REST endpoints + WS hub + agent relay
  backend/models.py      DB schema (users, conversations, terminals, messages)
  backend/schemas.py     request/response + WS event shapes
  agent/agent.js         the command executor (one-shot exec)
  frontend/lib/api.ts    REST client + connectWs
  frontend/lib/types.ts  TS mirror of schemas + WS event types
  frontend/components/ChatApp.tsx        WS wiring, reconnect, state
  frontend/components/TerminalPanel.tsx  xterm transcript + command input


================================================================================
A. MOST LIKELY FEATURE ADD-ONS (they pick ONE)
================================================================================

--- #1  Make `cd` / state persist  (VERY LIKELY — flows from your one-shot choice)
The single most probable ask, because it's the obvious "now make the terminal
real." They'll type `cd sub` then `dir` and see it ignored.
  Cheap live fix (~15 min): store a per-terminal cwd on the server; each run,
    prepend the saved cwd and detect `cd` to update it. Touches run_command +
    a Terminal.current_dir column (or an in-memory dict keyed by terminal_id).
    HONESTLY SAY: this still won't persist env vars / activated venvs / shells.
  Real fix (discuss, maybe don't code in 1hr): swap agent exec -> node-pty,
    one long-lived shell per terminal keyed by terminal_id, stream bytes.
  Be ready to explain WHY it doesn't persist today: exec spawns a child that
    changes ITS cwd then exits; next command starts fresh at root_folder.

--- #2  Live / streaming output  (LIKELY — UI copy already claims "streams live")
Right now output is one buffered blob returned after the command finishes.
  Approach: agent sends {type:"run_chunk", req_id, data} as stdout arrives
    (use spawn + stdout.on('data'), not exec); relay forwards each chunk as a
    new WS event; TerminalPanel writes chunks incrementally to xterm.
  Follow-on they may add: cancel a running command (Ctrl-C) -> needs the agent
    to keep the child handle by req_id and kill it on a {type:"cancel"} msg.

--- #3  Command history (up-arrow to recall)  (EASY, frontend-only — good quick win)
  Keep an array of submitted commands in TerminalPanel; ArrowUp/ArrowDown to
  cycle. No backend change. ~10 min. Good if they want something finished fast.

--- #4  Read-only / permissioned terminal sharing  (LIKELY — natural security ask)
  Add Terminal.mode ('run' | 'read_only') or an allowed-runners list. Enforce
  in run_command (403 if sender not allowed). Optionally: owner must approve
  each command (a pending state + approve endpoint + WS event).

--- #5  Group chat (3+ people)  (LIKELY as a DESIGN question; big as code)
  Today conversations are a SORTED PAIR (user_a, user_b) with a unique key.
  To generalize: add a participants join table (conversation_id, username);
  drop the pair key. The WS broadcast already fans out to a whole room, so
  live delivery barely changes. If they ask you to CODE it in 1hr, scope it to
  the schema + open-conversation change and say the broadcast is already N-way.

--- #6  Typing indicator / presence ("online", "typing…")  (LIKELY)
  IMPORTANT gotcha to raise: your WS is currently "notify-only" (clients never
  send over it; all actions are REST). Typing/presence is the first thing that
  wants client->server WS messages OR a separate presence channel. Good to
  discuss the tradeoff. Presence also replaces your 4s /users poll.

--- #7  Delete / edit a message  (EASY)
  New endpoint + a 'deleted'/edited flag + a WS event (message_updated); client
  updates by id. ~15 min.

--- #8  Message search or pagination  (EASY-MEDIUM)
  You currently load ALL messages for a conversation on open — they may point
  out this doesn't scale. Add limit/offset (or before-id cursor) to
  GET .../messages and load older on scroll.


================================================================================
B. MOST LIKELY BUGS THEY'LL PLANT OR ASK YOU TO EXPLAIN/FIND
================================================================================

1. "cd doesn't work" — presented as a bug. It's the one-shot design (see A#1).
   Explain the cause, then offer the fix. This is the highest-probability item
   in the whole interview.

2. Concurrent commands interleave in the transcript. Two commands run at once;
   a slow one's output lands after a later command's echo. Ordering is by
   message id (insert order), not completion. Cosmetic with one-shot; a REAL
   problem with a shared PTY (interleaved bytes) — know the difference.

3. Command escapes the shared folder. root_folder is only the cwd, not a jail.
   `cd ..`, absolute paths, `type C:\...\secret` all work. Fix = sandbox /
   allow-list / container, not just setting cwd.

4. Agent identity is spoofable. Agent just claims a name in agent_hello; the
   registry trusts it. Anyone can connect as "alice" and receive her command
   traffic / run as her. Fix = authenticate the agent (token/mTLS), bind to a
   real session.

5. No auth at all. Type-a-username, no password. CORS is allow_origins=["*"].

6. Big output. Agent maxBuffer is 10MB; a command exceeding it errors/truncates.
   Server also caps the wait at 30s; agent kills the child at 30s.

7. Agent disconnects mid-command. The server Future only resolves via the 30s
   timeout (returns "(no response…)"). A late reply after timeout is dropped
   safely (resolve finds no pending Future). Know this flow.

8. "User B can't run commands after a restart" (your old bug 2). Actually the
   xterm crash (bug 1) breaking B's render. The reconnect logic (onclose ->
   retry 1s + re-fetch + merge by id) means nothing is lost. Explain both.

9. xterm "Cannot read properties of undefined (reading 'dimensions')" (bug 1).
   Cause: opening a 0-size terminal + React StrictMode double-mount; the
   throwaway instance's scheduled syncScrollArea runs after dispose. Fix:
   open() only from a ResizeObserver once sized; ro.disconnect() cancels the
   discarded instance. (Already fixed — but they may ask you to explain it.)

10. SQLite: created with check_same_thread=False so FastAPI's threadpool can
    share the connection. Single-writer DB; fine for a demo, not for scale.


================================================================================
C. MOST LIKELY DISCUSSION QUESTIONS (no code — just answer well)
================================================================================

- "Where does a command actually run, and why?" -> owner's machine, via their
  agent; backend is a pure relay; browser is sandboxed so it can't run locally.

- "Why an agent instead of running on the server?" -> otherwise it's not the
  user's machine and it's RCE on your server.

- "Why one-shot instead of a real terminal (PTY)?" -> no native deps, no
  per-terminal process/state, no streaming protocol; demonstrates the sharing
  architecture. Cost: no persistent cd/env, no interactive programs, no
  streaming. Upgrade path = node-pty.

- "How do you match a reply to its request over one agent socket?" -> req_id
  (uuid) + asyncio.Future in AgentRegistry.pending; agent echoes req_id.

- "How would you scale to multiple backend instances?" -> Hub (rooms) and
  AgentRegistry (agent sockets) are in-memory per-process, so today you can't.
  Fix: Redis/NATS pub-sub for broadcasts; route agent traffic across instances
  (sticky by username or via the bus); move SQLite -> Postgres.

- "How does it survive a backend restart / offline client?" -> DB is the
  durable truth; clients reconnect (1s) and re-fetch + merge by id; agents
  reconnect + re-hello. Nothing lost.

- "Security?" -> RCE by design, no jail, no auth, spoofable agent, CORS *.
  Mitigate with auth (users + agents), sandbox/allow-list, folder jail,
  per-terminal permissions.
