  he wants in ALICE machine essentially hacking her pc, how would you suggest

● Great question — and it's exactly the kind of security design discussion
  they're likely to probe, since it flows straight from the "this is RCE by
  design" nature of the app. Here's how I'd think about it, no code.

  First, frame the problem honestly

  The whole product is "run commands on someone else's machine," so you can't
  eliminate execution — that's the feature. The goal isn't "stop commands," it's
  scope and confine them: make sure Bob can only do what Alice consented to,
  and that even a malicious command can't reach beyond a tiny blast radius. So
  there are really two independent questions: who is allowed to run, and what a 
  command is allowed to do. Good security answers both.

  Prerequisite: you must know who Bob actually is

  Before any restriction means anything, you need identity you can trust. Right
  now there's no real auth — anyone can log in as any name — and the agent's
  identity is spoofable (it just claims "I'm Alice's agent"). If Bob can just
  log in as Alice, or connect an agent as Alice, no permission rule matters. So
  step zero is: authenticate users (real sessions), and authenticate agents to
  their owner (a per-user token or mTLS, so the backend knows this really is
  Alice's machine, not something claiming to be). Everything below sits on top
  of that.

  Axis 1 — restrict WHO may run (authorization, cheap, done on the relay)

  This is enforced in the backend before it ever relays to the agent:

  - Read-only terminals — the simplest model. A terminal has a mode; if it's
  read-only, only the owner (Alice) can run, and Bob can only watch the output.
  This instantly kills the "Bob hacks Alice" default — but it also removes the
  collaboration, so it's more "share my screen" than "share control."
  - Owner-approves-each-command — the sweet spot for keeping collaboration. Bob
  proposes a command; it sits in a pending state; Alice sees it and clicks
  approve before it runs. Bob still participates, but Alice is the gate on her
  own machine. This is the honest answer to "let Bob help without trusting Bob."
  - Per-terminal allow-list of runners / roles — Alice explicitly grants "Bob
  may run" on a given terminal; default is watch-only. A middle ground.

  Note this axis controls who, not what — it reduces the trust boundary but if
  Bob (or Alice) is allowed to run, a command still has full power. That's why
  you need the second axis too.

  Axis 2 — restrict WHAT a command can do (confinement, the real fix)

  Here you assume a command will be hostile and make sure it can't hurt Alice:

  - Least-privilege execution account — biggest bang for the buck. Run the
  spawned commands as a dedicated low-privilege OS user that can only touch the
  shared folder and nothing else — not Alice's documents, not admin, not her SSH
  keys. Even type C:\secret fails because that user has no rights to it.
  - A real filesystem jail — today root_folder is only the starting directory;
  cd .. and absolute paths escape it freely. A true jail (OS ACLs on that
  restricted user, a chroot-style confinement, or a container with only the
  folder mounted) makes "outside the folder" genuinely unreachable, not just
  "not where you start."
  - Containerization / isolation — the strongest: run commands inside a
  container or VM with only the shared folder bind-mounted, no network (blocks
  exfiltration and downloading tools), and resource/time limits (CPU, memory,
  the 30s timeout you already have). The blast radius becomes "one throwaway
  sandbox," not "Alice's whole machine."

  Why command-string filtering is a trap (worth saying out loud)

  The tempting idea is "just block dangerous commands like del/rm/format." Don't
  rely on it. A shell is a programming language — Bob bypasses a blocklist
  trivially with aliases, pipes, cmd /c, base64-encoded PowerShell, calling a
  script, or a different binary that does the same thing. An allow-list (only
  permit dir, git status, etc.) is strictly better because it fails closed, but
  it also kills the terminal's usefulness and is still fragile once you allow
  anything that can chain (&&, subshells). So treat string filtering as a
  defense-in-depth extra, never the primary control.

  What I'd actually do, in order

  1. Auth first (users + agents) — otherwise nothing else is enforceable.
  2. Add a permission model — default new terminals to read-only, with an
  explicit owner-approval flow for collaboration. This is the piece that's
  realistically codeable in an interview time-box: it's a mode field on the
  terminal, a check in the relay before running, plus a small UI change. It
  directly answers "Bob can't freely run on Alice's machine anymore."
  3. Confine execution — run commands as a dedicated least-privilege user, 
  jailed to the shared folder, with no network and resource limits, ideally in a
  container. This is the OS-level "here's how I'd really secure it" part —
  bigger than a live coding slot, but it's the answer that shows you understand
  the actual threat.

  The one-sentence version for the interview: "I'd stop trusting the network 
  (authenticate users and agents), put Alice in control of what runs on her 
  machine (read-only by default, or approve-each-command), and then assume every
  command is hostile and confine it — least-privilege user, folder jail, no 
  network, resource limits, ideally a container — because blocklisting commands 
  is whack-a-mole you always lose."

● Solid instinct — "keep it in the folder" is the right first thing to reach
  for. But the honest answer is: it helps, it doesn't fix it, and how you
  implement it matters enormously — one way is real security, the other is an
  illusion. Let me walk through it, then compare to Docker.

  Would "only allow commands in the same directory" fix it? Short answer: no, 
  partially.

  It closes one hole (reading/writing outside the shared folder) and leaves
  several others wide open. And it only closes even that hole if you enforce it
  the right way.

  The critical fork: there are two totally different ways to "restrict to the 
  directory"

  Way A — inspect the command text (reject cd .., absolute paths, etc.). This 
  does not work. It's the same whack-a-mole as blocklisting, because a shell
  command has infinite ways to reach outside a folder that you can't reliably
  detect by reading the string:
  - absolute paths (type C:\Users\alice\secret.txt)
  - environment variables (%USERPROFILE%, $HOME)
  - pushd, symlinks, UNC paths, Windows 8.3 short names
  - calling another program that reads anywhere (powershell, python -c ...)
  - a script file that does the escaping for you

  You can't parse your way to safety — the shell is a full programming language.
  So if "restrict to directory" means checking the command, it gives a false
  sense of security and Bob escapes in seconds.

  Way B — enforce it at the OS level. Run the command as a dedicated 
  low-privilege user whose filesystem permissions (ACLs) grant access to only
  the shared folder and deny everything else. Now it doesn't matter how Bob
  writes the command — the moment it touches C:\Users\alice\..., the operating 
  system refuses, because that account simply has no rights there. This is real,
  because the enforcement is below the shell, not in front of it.

  So the first lesson: "restrict to the directory" only means anything if the OS
  enforces it, not if you validate the command string.

  How I'd implement the real (OS-enforced) version

  - Create a dedicated restricted OS account for running shared commands (not
  Alice's own account).
  - Set filesystem ACLs so that account can read/write only the shared folder —
  explicitly denied access to Alice's profile, system directories, everything
  else.
  - Run each spawned command as that account instead of as Alice.
  - (You'd also have to be careful about the sneaky bits: temp directories, the
  account's own profile, anything world-readable.)

  That's genuinely better than today. But notice what it still doesn't stop.

  What even a perfect directory jail does NOT stop

  Confining the filesystem to one folder leaves these open:
  - Network — curl evil.com, exfiltrate the folder's contents, download and run
  malware, open a reverse shell. A filesystem jail doesn't touch the network at
  all.
  - Resource exhaustion / DoS — a fork bomb or an infinite loop can pin the
  CPU/RAM (your 30s timeout helps, but a fork bomb does damage in far less than
  30s).
  - Process privileges — the command still runs as a real OS process; depending
  on that account's rights it may see other processes, env vars, hardware, etc.

  So a directory jail is one dimension of isolation (filesystem), and security
  needs several. That's exactly the gap Docker fills.

  Compare: Docker (containerization)

  Docker isn't "a better folder restriction" — it isolates all the dimensions at
  once, which is why it's the real answer:

  - Filesystem — instead of hand-writing ACLs, the container simply doesn't 
  contain the host's filesystem. You bind-mount only the shared folder; Alice's
  real files literally don't exist inside that world. "Escaping the directory"
  isn't blocked — there's nothing to escape to.
  - Network — run it with networking off (--network none). No exfiltration, no
  downloads. One flag.
  - Process isolation — the command runs in its own process namespace; it can't
  see or touch host processes.
  - Privileges — run as a non-root user inside the container, and even a full
  compromise is still trapped inside the container boundary.
  - Resource limits — CPU, memory, and process-count caps are built in
  (fork-bomb protection included).
  - Disposable — you throw the container away after each use, so any mess is in
  a sandbox you were going to delete anyway, and Bob always gets a clean one.

  In other words, the directory-ACL approach is you manually building one wall;
  Docker gives you all the walls, plus a self-destruct, in a single
  well-understood mechanism.

  Docker's costs (the trade-offs to name)

  It's not free, and a sharp interviewer will want you to know why you might not
  use it:
  - Heavy dependency — Alice needs Docker installed and running; that's a big
  ask versus a dependency-free Node agent.
  - It changes what "her terminal" means — the whole product promise was "run on
  the sharer's actual machine": her folder, her installed tools, her
  environment. Inside a container, none of that is there unless you
  mount/install it. So you trade authenticity for isolation — that's a genuine
  product tension, not just a technical one.
  - Windows/Linux UX wrinkle — Docker on Windows means Linux containers (via
  WSL2). Suddenly Bob's dir should be ls, and the whole environment is Linux,
  not Alice's Windows box. For this specific demo that's a real mismatch.

  Bottom line

  - Directory restriction = lightweight, runs in Alice's real environment, but
  only one layer (filesystem) and only real if OS-enforced. A good necessary
  step, not a complete fix.
  - Docker = comprehensive containment (filesystem + network + process +
  resources + disposable) in one mechanism — the actual answer to "assume the
  command is hostile" — at the cost of a heavy dependency and losing the "her
  real machine" authenticity.

  The mature framing for the interview: "Restricting to the folder only counts 
  if the OS enforces it, not if I parse the command — and even then it only 
  stops filesystem escape, not network or resource abuse. Docker is stronger 
  because it isolates all of those at once and is disposable; the price is a 
  heavy dependency and that it's no longer literally her environment. So 
  realistically I'd combine layers: a permission model for who can run, and a 
  container for what a command can do — with the folder jail being something the
  container gives me for free."

● Good — this gets at the elegant part of the design, and the honest limit of
  it. The short answer: yes, it works, and the file really does end up in 
  Alice's folder and stays there. Here's why, and what it means.

  Why it works: the shared folder is a live window, not a copy

  When you use Docker, you don't copy Alice's folder into the container — you
  bind-mount it. A bind mount is a two-way live window: the folder inside the
  container is the same folder on Alice's real disk. So when Bob runs a command
  that creates newfile.txt in that folder inside the container, the write goes
  straight through the mount to Alice's actual folder. Alice sees the new file
  appear. It's real, and it persists.

  And crucially — it survives the container being destroyed. Remember the
  container is disposable: anything Bob writes outside the shared folder (in the
  container's own throwaway filesystem) vanishes when the container is thrown
  away. But the shared folder isn't part of the container's throwaway layer — it
  lives on Alice's host — so files Bob creates there stay. That's exactly the
  behavior you want: the shared folder is the one durable output, everything
  else is scratch that gets cleaned up.

  The mental model

  The bind-mounted shared folder is a deliberate hole in the isolation — the
  single, agreed-upon place where the two worlds intentionally share state.
  Legitimate work flows through it in both directions. The security boundary is
  drawn around that folder: everything outside it (Alice's other files, the
  system, the network, other processes) is isolated and disposable; the folder
  itself is the shared workspace.

  The honest catch: inside the folder, Bob still has power

  Here's the part to say out loud in an interview, because it's the real limit
  of the Docker fix: Docker protects everything outside the shared folder, but 
  not the contents inside it. If you mounted it read-write so Bob can create
  files, then Bob can also:

  - modify Alice's existing files in that folder,
  - delete them (del *),
  - fill the folder up with junk (bounded by a disk quota if you set one).

  So Docker shrinks the blast radius from "Alice's whole machine" down to "the
  one folder Alice chose to share" — a massive reduction, but not zero. The
  shared folder is the trust boundary, and Bob is trusted within it.

  The knob that decides this: read-only vs read-write mount

  You get to choose when you mount:

  - Read-write mount — Bob can create/edit/delete in the folder (his "make a new
  file" scenario works). Good for genuine collaboration, but Alice is trusting
  Bob with that folder's contents.
  - Read-only mount (:ro) — Bob can look but not change anything; his echo > 
  newfile.txt would fail with "permission denied." Good for "let them safely
  explore my project" — and this pairs naturally with the read-only permission
  model from before.

  So this maps right back to the earlier discussion: Docker answers "what can a 
  command touch" (only the folder), and the permission model / mount mode 
  answers "how much do I trust Bob within the folder." If Alice fully trusts
  Bob, read-write. If not, read-only mount, or the owner-approval flow so she
  gates the risky ones. That combination — container for the outer boundary,
  mount mode + approvals for the inner one — is the complete answer.

  One small practical wrinkle worth a mention: on Linux containers, a file Bob
  creates gets the container user's ownership, which can show up with odd
  permissions on Alice's host. It's a housekeeping annoyance, not a security
  issue, and it's usually smoothed over on Windows/WSL2 mounts — but it's the
  kind of detail that shows you've actually thought about running this, not just
  diagrammed it.

● Good — this is the "least-privilege account, OS-enforced" path, and it's the
  right lighter-weight alternative to Docker on Windows. The core idea in one
  line: you stop trusting the command and let the operating system's own 
  permission checks be the jail — the command runs under an account that
  physically lacks the rights to touch anything but the shared folder, so it
  doesn't matter how cleverly the command is written. Here's how I'd build it on
  Windows.

  The core mechanism

  Two OS features do the enforcement, and they sit below the shell so they can't
  be talked around:

  1. A dedicated low-privilege user account (say termchat_runner) — the commands
  run as this account, not as Alice.
  2. NTFS file permissions (ACLs) — this account is granted access to the shared
  folder and nothing sensitive. When a command tries to read
  C:\Users\alice\secret.txt, Windows itself returns "access denied," because the
  account has no right to it. No parsing, no blocklist — the kernel refuses.

  The important insight: you get a big chunk of this almost for free. On
  Windows, each user's profile (C:\Users\alice) is already ACL'd to that user +
  admins only. So the moment a command runs as a different standard user, it
  already cannot read Alice's personal files. That's the single biggest risk
  (reading her secrets) gone just by switching accounts. The explicit ACL work
  is then about granting the runner access to the one folder it should reach.

  How I'd implement it — one-time setup (admin)

  1. Create the runner account — a local standard user, not an administrator,
  with minimal group membership and no interactive-logon rights it doesn't need.
  This is who commands execute as.
  2. Set the folder ACLs — grant termchat_runner modify rights on the shared
  folder(s), so commands can actually work there (create/edit files, as we
  discussed). Rely on default profile isolation to keep Alice's other files
  unreadable; optionally add explicit deny rules on especially sensitive paths.
  3. Give the agent a way to launch processes as that account — this is the
  Windows-specific hurdle (below).

  How I'd implement it — per command (runtime, in the agent)

  4. Run the command as termchat_runner instead of as the current user. On
  Windows the mechanism is CreateProcessWithLogonW (log the runner in with its
  stored credentials and spawn the child in its context) or CreateProcessAsUser
  (needs a token and a privileged agent). The child's working directory is the
  shared folder — but remember, cwd is not the jail; the ACLs are. cwd just sets
  where it starts.
  5. Wrap the child in a Windows Job Object — this is how you close the resource
  holes: cap CPU, memory, and process count (kills fork bombs), and set
  "terminate on close" so your 30-second timeout reliably kills the whole
  process tree, no orphans.
  6. Optionally tighten further — launch the child at Low integrity level (a
  Low-integrity process can't write to most of the filesystem even where ACLs
  might otherwise allow it), or go all the way to an AppContainer (Windows'
  built-in sandbox, which can also restrict network). And add a per-user Windows
  Firewall rule that blocks outbound network for the runner account, to stop
  exfiltration.
  7. Capture stdout/stderr and return the output exactly as the agent does
  today.

  The honest catches (say these in the interview)

  - The Node friction is the real work. Node's child_process runs everything as
  the same user — it has no built-in "run as another user." So you need a small 
  native helper (a native addon or a tiny launcher exe) that calls
  CreateProcessWithLogonW. On Linux this would be trivial (sudo -u, setuid); on
  Windows it's this API dance. That's the main piece of new code.
  - Filesystem confinement alone is not full security — same point as before.
  Running as a restricted user stops file access outside the folder, but not
  network exfiltration or resource abuse. That's exactly why steps 5 and 6 (Job
  Object + firewall/AppContainer) matter — without them, Bob can still curl your
  data out or spin the CPU. "Least privilege" has to mean all the privileges,
  not just files.
  - "Only the shared folder and nothing else readable" is impractical in the 
  strict sense — any program needs to read system DLLs, cmd.exe, etc., just to
  run. So the realistic goal is "can't read Alice's data and can't write outside
  the folder," not "can't read a single byte anywhere else." Be precise about
  that when you describe it.
  - Cross-folder leakage with one shared runner — subtle but worth raising: if
  Alice shares folder X with Bob and folder Y with Carol, and both are ACL'd to
  the same termchat_runner, then a command Bob runs (confined to the runner) can
  still reach Y. True per-terminal isolation would need a separate runner 
  account per shared folder (or per guest), or re-applying ACLs per command. For
  a single sharer it's often acceptable; for strict isolation it's a real
  design choice.
  - The irony vs Docker — doing this properly (restricted token + Job Object +
  AppContainer + per-user firewall) ends up hand-assembling most of what a
  container gives you in one flag each. It's lighter on dependencies (no Docker
  install, and it genuinely runs in Alice's real environment with her real tools
  — which preserves the "her machine" authenticity you liked), but you're
  building each isolation dimension yourself instead of getting them bundled.

  The one-sentence framing

  "I'd run each command under a dedicated standard user whose NTFS permissions 
  grant only the shared folder, so the kernel — not a command parser — enforces 
  the boundary; then layer on a Job Object for resource limits and a per-user 
  firewall or AppContainer for network, because filesystem isolation alone 
  doesn't stop exfiltration or fork bombs. It keeps Alice's real environment 
  (unlike Docker) at the cost of hand-building each layer, and the one native 
  piece I need is a helper to launch the child as that user, since Node can't do
  that itself."

  and where the run-as-user helper would slot into agent.js's runCommand?

● Yes — and this is actually the clean way to do it. NTFS permissions are fully 
  dynamic: you can grant or revoke a specific account's access to a folder at
  any moment while the agent is running. Nothing has to be decided up front.
  Here's how it fits together and the one trap to watch.

  Yes, ACLs are a runtime operation

  When Alice shares a new folder, the agent adds an ACL entry granting
  termchat_runner access to that exact folder; when she stops sharing it, the
  agent removes that entry. On Windows the tools for this are icacls (command
  line), PowerShell's Set-Acl, or the Win32/.NET security APIs — all scriptable,
  all effective immediately. So the runner account's reachable set can grow and
  shrink to match "whatever Alice is sharing right now."

  Who's allowed to change the permissions (this part works out nicely)

  To modify a folder's ACL you must own it or have admin. Alice owns her 
  folders, so the agent — which runs as Alice — can grant the runner access to 
  Alice's folders without needing admin at all.* That gives you a clean split of
  duties:

  - Agent = Alice → has the right to hand out folder access (and to change
  ACLs).
  - Runner = low-privilege → actually executes Bob's commands, confined by those
  ACLs.

  The privileged "grant" step and the unprivileged "execute" step are cleanly
  separated, which is exactly what you want.

  The natural lifecycle: grant on share, revoke on unshare

  Tie the ACL changes to events you already have:

  - On share (/terminals/share) → grant the runner access to that folder.
  - On revoke (/terminals/revoke) → remove the grant.

  Then the runner's access set is always exactly "the folders currently shared"
  — dynamic, and self-cleaning as long as you revoke properly.

  The trap: accumulating grants brings back cross-folder leakage

  Here's the thing to be careful about. If you only ever grant and never revoke,
  the runner slowly accumulates access to every folder Alice has ever shared.
  And even at a single moment, if Alice is sharing folders X and Y
  simultaneously, one runner account with access to both means a command in 
  terminal X can still reach Y. Runtime granting makes access dynamic; it does
  not by itself make terminals isolated from each other. So you have to pick
  your isolation model:

  - One runner + dynamic ACLs (simplest). The runner can reach all 
  currently-shared folders. Perfectly fine if you accept "everything Alice is
  deliberately sharing right now is mutually OK to expose" — which for a single
  user's session is usually true. Simplest to manage: one account, grant/revoke
  as folders come and go.
  - A runner account per folder (or per guest). Each account only ever has one
  folder, so there's zero cross-folder leakage — strong isolation. The cost is
  heavier account management: creating/destroying OS accounts (which needs
  admin), and juggling each account's credentials for the run-as-user launch.
  - A small pool of runner accounts, one assigned per active terminal, re-ACL'd
  on assignment. A middle ground between isolation and account churn.

  One concurrency caveat

  Don't try to grant right before each command and revoke right after, if you're
  using a single shared runner — overlapping commands from two terminals would
  race (one command's revoke yanks access out from under another that's still
  running). Tie the ACL changes to the share/revoke lifecycle, not to individual
  command execution. (Per-folder accounts sidestep this entirely, since each
  account's access is stable for the life of that terminal.)

  One small architectural addition you'll need

  Today the agent only receives run requests with a cwd — it doesn't hear about
  share/revoke events. To grant-on-share cleanly, you'd either:

  - have the backend notify the agent of share/revoke (a small new message type
  on the agent socket), or
  - have the agent grant lazily — the first time it sees a command for a new
  folder, grant access (idempotent), and revoke on a revoke signal or on agent
  shutdown.

  Either works; just don't forget the cleanup — revoke on unshare and on agent
  exit — or stale grants pile up and the runner quietly regains the broad access
  you were trying to prevent.

  What I'd do for this app

  One runner account, grant on share / revoke on revoke, accept that Alice's
  currently-shared folders are mutually reachable (they're all things she
  deliberately exposed). It's the least machinery for the biggest win — Bob
  still can't touch anything Alice isn't sharing. If an interviewer pushes for
  strict per-terminal isolation, that's your cue to escalate to per-folder 
  runner accounts and explain the account-management trade-off.

  command runs inside a throwaway container with only the specific shared folder
  bind-mounted, so the container can touch that folder and nothing else. And
  here's the elegant part for your codebase: the folder to mount is already
  handed to the agent on every command (it's the cwd in each run message), so
  this is a change to one function — how the agent executes — with no protocol 
  change. Here's the step-by-step.

  The key design choice: one container per command (ephemeral)

  Match your existing one-shot design: for each command, docker run --rm a fresh
  container, mount the folder, run, capture output, container self-destructs.
  This fits perfectly because you already have no persistent state between
  commands — cd doesn't stick today, and it won't here either, which is
  consistent. (A per-terminal long-lived container is the upgrade for
  persistence/speed — Phase 5.)

  Phase 0 — One-time setup on the sharer's machine

  1. Install Docker Desktop and make sure it's running (it must be up whenever
  Alice shares).
  2. Pull a small base image once: docker pull alpine (or build a custom image
  preloaded with whatever tools you want available inside).
  3. Confirm the drive is shareable — with Docker Desktop's WSL2 backend,
  Windows paths mount fine; just know the shared folder must be in a location
  Docker is allowed to mount.

  Phase 1 — Swap the executor in agent.js

  This is the core change. In runCommand(command, cwd), instead of running the
  command directly on the host, run it inside a container with the folder
  mounted:

  docker run --rm --name termchat_<reqId> \
    --network none \
    --memory 256m --cpus 1 --pids-limit 128 \
    --cap-drop ALL \
    --read-only --tmpfs /tmp \
    -v "<cwd>:/work" -w /work \
    alpine sh -c "<the user's command>"

  - -v "<cwd>:/work" is "mount it on the specific folder" — Alice's shared
  folder becomes /work inside; -w /work starts the command there.
  - The command's stdout/stderr stream back through the docker run process, so
  your existing output capture, the 10MB cap, and stderr-merging all still work
  — you're just spawning docker instead of the raw command.

  One critical security detail: build this with spawn('docker', [ ...flags, 
  'sh', '-c', userCommand ]) using an args array — not exec('docker run ... ' + 
  userCommand). If you string-concatenate the user's command into a host shell
  line, Bob can break out of the docker run invocation on the host and you've
  sandboxed nothing. Passing his command as a single argument to sh -c keeps it
  trapped inside the container.

  Phase 2 — The security flags (this is the whole payoff)

  Each flag closes one of the holes we discussed earlier:

  - --rm → disposable; the container (and anything Bob wrote outside /work)
  vanishes after.
  - --network none → no exfiltration, no downloads — closes the network hole the
  ACL approach couldn't.
  - --memory / --cpus / --pids-limit → fork-bomb and resource-exhaustion 
  protection.
  - --cap-drop ALL → strips Linux capabilities.
  - --read-only --tmpfs /tmp → the container's own filesystem is read-only
  except a scratch /tmp; the only writable place is the mounted folder.
  - (Optional --user) → run as non-root inside; note Docker Desktop's Windows
  bind mounts are usually permissive enough that non-root can still write to
  /work, but that's worth a quick test.

  Phase 3 — Timeout and cleanup

  docker run has no self-timeout, so keep your existing 30s timer. Because you
  named the container termchat_<reqId>, on timeout you kill it
  deterministically:

  docker kill termchat_<reqId>   (and docker rm -f as a belt-and-suspenders)

  --rm handles the normal case; the named kill handles the hung case. Same
  graceful "(timed out after 30s)" message flows back as today.

  Phase 4 — What does NOT change, and the things to flag

  No protocol change, no share/revoke wiring. Because the mount source is just
  the cwd on each run request, the backend, the transcript, the WebSocket relay,
  the req_id/Future correlation — all untouched. Concurrent commands are
  naturally isolated because each gets its own uniquely-named container. This is
  much simpler than the ACL approach, which needed grant/revoke messages.

  Two honest caveats to raise in the interview:

  - The environment becomes Linux. Docker Desktop runs Linux containers, so
  Bob's commands are Linux (ls, not dir). Your UI examples use dir — you'd
  either switch the demo to Linux commands, or use a heavier Windows container 
  image (nanoserver/servercore) to keep cmd/PowerShell. Say this out loud; it's
  the real consequence of "it's no longer literally her Windows machine."
  - Per-command startup cost. A fresh docker run is
  sub-second-to-a-couple-seconds. Fine for a demo; the fix if it matters is
  Phase 5.

  Phase 5 — The upgrade: one long-lived container per terminal

  If they push on performance or want cd/state to persist:

  - On share (/terminals/share): start a detached container for that terminal
  with the folder mounted — docker run -d --name term_<id> ... alpine sleep 
  infinity.
  - Per command: docker exec term_<id> sh -c "<command>" — faster (no
  per-command startup) and can hold state.
  - On revoke (/terminals/revoke): docker rm -f term_<id>.

  This is where the grant/revoke protocol from the earlier discussion comes back
  — you'd send the agent start/stop signals tied to share/revoke, and clean up
  containers on agent shutdown. It's the container analog of the per-terminal
  model, and a natural "here's how I'd make it production-grade" follow-up.

  The end-to-end picture

    → backend relays run {command, cwd:"C:\proj"} → agent
    → agent spawns:
        docker run --rm --network none ... -v "C:\proj:/work" -w /work

  discarded
    → stdout returned to the transcript exactly as before

  What changes in your codebase: essentially just agent.js's runCommand (spawn
  docker run with the mount + security flags instead of raw exec, plus
  container-kill on timeout). Optionally Phase 5 adds share/revoke container

  cat ../../../HW5.pdf

  In docker mode, expected:
  cat: can't open '../../../HW5.pdf': No such file or directory
  → blocked. The container can't climb above its own root, and your Desktop
  isn't mounted, so the PDF is simply unreachable.

  Cleaner ways to test (since HW5.pdf is binary, cat would spew garbage if it
  did work — these avoid that):
  ls -la ../../../HW5.pdf     # can it even SEE the file? docker: "No such file
  or directory"
  wc -c ../../../HW5.pdf      # byte count — proves read access; docker: fails,
  no access
  head -c 100 ../../../HW5.pdf   # first bytes (would start with "%PDF" if
  readable)

  All three should fail in docker mode.

  The proof it means something: if you restarted the agent in normal mode (no
  AGENT_SANDBOX=docker) and shared the same folder, the Windows equivalent type 
  ..\..\..\HW5.pdf would actually read the file — that's the escape you found.
  In docker mode the same attempt can't reach it. Run pwd first to confirm it
